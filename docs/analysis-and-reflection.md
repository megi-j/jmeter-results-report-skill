# Custom Skill: `jmeter-results-report`

## ნაბიჯი 1 — ანალიზი

### რა რუტინულ საქმეს ვირჩევ და სად შევხვდი კურსზე?

**JMeter-ის ტესტის non-GUI გაშვება და შედეგების ანგარიშის (Performance Results) მომზადება NFR-ებთან შედარებით.**

Performance testing-ის ბლოკში ეს საქმე თითქმის ყველა დავალებაში მეორდებოდა:

- **jmeter-homework** — restful-booker Create Token API-ის ტესტ-გეგმა + NFR დოკუმენტი;
- **jmeter-elements** — Thread Groups, reqres.in users API;
- **JDBC + API** — SQL Server-ის `TestUsers` ცხრილი და reqres.in, non-GUI გაშვება CSV შედეგებით;
- **Demo Web Shop** — ჩაწერილი user journey, HTML რეპორტი და Performance Results დოკუმენტი.

ყოველ ჯერზე ტესტ-გეგმა სხვა იყო, მაგრამ „გაშვება → რეპორტი → ციფრების წაკითხვა → NFR-თან შედარება → დოკუმენტის დაწერა“ ერთი და იგივე.

### როგორ კეთდება ეს ახლა ხელით?

1. ვიპოვი `.jmx` ფაილს და ვამოწმებ, რომ GUI-ში აწყობილი listener-ები (View Results Tree, Summary Report) გამორთულია.
2. ტერმინალში ვწერ `jmeter -n -t plan.jmx -l results.jtl -e -o report` ბრძანებას.
3. თუ `report` ფოლდერი უკვე არსებობს — JMeter ერორს აგდებს, ვშლი ან ახალ სახელს ვარქმევ და თავიდან ვუშვებ.
4. ვხსნი `report/index.html`-ს და Statistics ცხრილიდან ვიწერ ყოველი sampler-ის avg, p90, p95, p99, error %, throughput.
5. დავალების ტექსტიდან / NFR დოკუმენტიდან ვიღებ ზღვრებს (მაგ. p95 ≤ 1000 ms, errors ≤ 1%).
6. თითოეულ sampler-ს ხელით ვადარებ ზღვარს და ვწერ PASS/FAIL.
7. Errors ჩანართში ვამოწმებ, რა იყო შეცდომების მიზეზი (assertion, 429, timeout).
8. ვწერ Performance Results დოკუმენტს: ცხრილი, ვერდიქტი, დასკვნები, ეკრანის ანაბეჭდები.

ყველაზე დიდ დროს 4–6 ნაბიჯი იღებს და აქვეა შეცდომის რისკი — ციფრის არასწორად გადაწერა ან ერთი sampler-ის გამოტოვება.

### Input და Output

| Input | Output |
|---|---|
| ტესტ-გეგმა `*.jmx` | `results/<run-id>/results.jtl` — ნედლი შედეგები |
| NFR ზღვრები (`nfr.json` ან დავალების ტექსტი) | `results/<run-id>/html/` — JMeter-ის HTML dashboard |
| დატვირთვის პროფილი (threads, ramp-up, duration) | `summary.json` — ყველა მეტრიკა მანქანისთვის |
| ან უკვე არსებული `.jtl` ფაილი | `performance-report.md` — ცხრილი, NFR-ის შემოწმება, შეცდომები, დასკვნები |

### სად სჭირდება აუცილებლად ადამიანის გადაწყვეტილება?

1. **NFR ზღვრების დადგენა** — აგენტმა არ უნდა მოიგონოს, რა არის „კარგი“ response time. ეს ბიზნესის / დავალების მოთხოვნაა. თუ ზღვრები არ არის მოცემული, Skill ეკითხება ან placeholder-ად ნიშნავს.
2. **დატვირთვის პროფილი** — რამდენი მომხმარებლით „დავტვირთოთ“ სხვისი საჯარო სერვისი (reqres.in, restful-booker), ეს ადამიანმა უნდა გადაწყვიტოს.
3. **საზღვრული (borderline) შედეგების შეფასება** — როცა მნიშვნელობა ზღვრის 10%-ის ფარგლებშია (REVIEW), ან შეცდომები rate limit-ით (429) არის გამოწვეული. მისაღებია თუ არა, ან უნდა გაეშვას თავიდან — ადამიანის გადაწყვეტილებაა.
4. **მონაცემების გაფილტვრა** — warm-up-ის ამოჭრა ან label-ების გამორიცხვა ანგარიშის მტკიცებას ცვლის, ამიტომ აგენტი მხოლოდ სთავაზობს.

## ნაბიჯი 2 — სტრუქტურის შესწავლა (მოკლედ)

`maven-codegen-kit`-იდან ავიღე:

- **description** აღწერს, *როდის* გამოიყენოს აგენტმა Skill — მათ შორის მაშინაც, როცა რაღაც გაფუჭდა (empty folder, duplicate class) — და არა მხოლოდ რას აკეთებს.
- **„Detect before asking“** — ჯერ პროექტს კითხულობს (`grep`, `ls`), მერე სვამს მხოლოდ ღია კითხვებს, რეკომენდებული ვარიანტით.
- **SKILL.md მოკლეა**, დეტალები `references/`-შია (progressive disclosure).
- **Failure modes ცხრილი** — სიმპტომი → მიზეზი, ერთ ადგილას.
- **„არ თქვა წარმატება, რომელიც არ გინახავს“** — თუ ინფრასტრუქტურა არ არის, მომხმარებელს ზუსტ ბრძანებას აძლევს.

## ნაბიჯი 3 — Skill-ის სტრუქტურა

```
jmeter-results-report/
├── SKILL.md                    ← name, description, 6-ნაბიჯიანი workflow
├── scripts/
│   ├── run_jmeter.sh           ← non-GUI გაშვება, ახალი ფოლდერი ყოველ run-ზე, CSV ველების იძულება
│   └── analyze_jtl.py          ← .jtl → სტატისტიკა + NFR შემოწმება (PASS / REVIEW / FAIL)
├── references/
│   ├── jmeter-cli.md           ← CLI flags, -J პარამეტრები, failure modes ცხრილი
│   └── metrics.md              ← მეტრიკების განმარტება, percentile-ის ფორმულა, ვერდიქტის წერა
└── assets/
    ├── nfr-template.json       ← NFR ფაილის ფორმატი
    └── report-template.md      ← ანგარიშის შაბლონი
```

`analyze_jtl.py` p90/p95/p99-ს იმავე ფორმულით ითვლის, რომლითაც JMeter-ის HTML dashboard (Apache Commons Math „legacy“ estimator), ამიტომ ციფრები dashboard-ს ემთხვევა. მხოლოდ Python-ის სტანდარტულ ბიბლიოთეკას იყენებს. სინთეზურ `.jtl`-ზე (600 sample, 2 label) გამოცდილია: სწორად ითვლის მეტრიკებს, ავლენს FAIL/REVIEW-ს და აჯგუფებს შეცდომებს (`429 Too Many Requests ×7`).

## ნაბიჯი 4 — რეფლექსია

ჩემი Skill არ აწყობს და არ ასწორებს თავად `.jmx` ტესტ-გეგმას — ის მხოლოდ უშვებს მზა გეგმას და აანალიზებს შედეგს; ასევე კითხულობს მხოლოდ CSV ფორმატის `.jtl`-ს (არა XML-ს), არ ადარებს ორ სხვადასხვა გაშვებას ერთმანეთს და `.docx` დოკუმენტს პირდაპირ არ ქმნის. მომავალში დავამატებდი run-ებს შორის შედარებას (baseline vs. ახალი გაშვება, რეგრესიის აღმოჩენით), გრაფიკების ავტომატურ ჩასმას ანგარიშში და K6-ის შედეგების მხარდაჭერას, რადგან კურსზე K6 სკრიპტებიც გვქონდა იმავე NFR-ებით.
